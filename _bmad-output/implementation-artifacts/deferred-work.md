## Deferred from: code review of 3-4-ne-jamais-remontrer (2026-09-14)

- **`permissions: contents: write` sur `pipeline-nocturne.yml` élargit le rayon d'action de tout le job, pas seulement de l'écriture de `data/deja-vu.sqlite3`.** Avant cette story, le jeton ambiant du job était `contents: read` ; il porte désormais un droit d'écriture sur l'intégralité du dépôt source pendant toute la durée du run. Si une future faille d'exécution de code survenait pendant le run (dépendance compromise via `uv sync`, bug de parsing exploité par un flux malveillant), le rayon d'action passerait d'une simple exfiltration de secrets à une possibilité de modification directe du dépôt (code, tests, historique). Compromis assumé, propre à l'architecture choisie (SQLite committé dans le dépôt source via l'API Contents, Story 3.4) : GitHub Actions ne permet pas de scoper `permissions` à un seul step ni à un seul chemin de fichier, donc aucune réduction supplémentaire n'est possible sans changer d'approche de persistance (service de stockage dédié, hors scope NFR1 — gratuité). À revisiter seulement si le pipeline gagne un jour une surface d'exécution de code non maîtrisée plus large qu'aujourd'hui (`.github/workflows/pipeline-nocturne.yml`).
- **Aucune stratégie de purge/rétention sur la table `deja_vu`.** Chaque clé d'identité marquée « vue » reste en base indéfiniment, sans TTL ni archivage. Sans conséquence à l'échelle actuelle (identifiants seuls, pas de contenu — fichier resterait minuscule pendant des années à ce volume), mais aucun plan ni test ne couvre la croissance sur un horizon long. À traiter si la taille du fichier synchronisé devient un jour un problème réel (`src/veille/store.py`).
- **Le champ `content` de l'API Contents de GitHub a un plafond (~1 Mo) au-delà duquel GitHub omet/tronque le contenu base64 de la réponse.** `synchroniser_depuis_distant`/`televerser_vers_distant` dégraderaient silencieusement (capturé par le `except Exception` englobant, donc sans planter, mais sans alerte non plus) si `data/deja-vu.sqlite3` venait un jour à approcher ce plafond. Le fichier ne contient que des identifiants d'articles (pas leur contenu), donc la croissance attendue est lente — mais rien ne surveille l'approche du seuil. À traiter si la table `deja_vu` grossit significativement (voir l'entrée de rétention ci-dessus, cause probable commune). (`src/veille/store.py`)

## Deferred from: code review of 1-1-collecte-premiere-source (2026-07-28)

- **Collision de `guid` de repli sur `source_id + titre`.** Deux entrées sans lien ni id partageant un titre générique (ex. "Weekly Update") produisent le même hash et collapsent silencieusement. Sans conséquence tant qu'aucune logique de dédoublonnage n'existe (Story 1.1) — devient consequential dès la **Story 1.3** (dédoublonnage), à traiter à ce moment-là.
- **Aucun timeout réseau sur `feedparser.parse()`.** Une source qui ne répond jamais bloquerait indéfiniment tout le run. Relève explicitement d'**Epic 2** (Story 2.2 tolérance aux pannes, Story 2.3 sources sensibles au débit).

Recoupe directement **Epic 4** (FR-12/FR-13, détection et signalement des sources défaillantes) — à intégrer à ce moment plutôt qu'en scope creep maintenant.

L'AC2 actuel n'exige que la présence des champs, pas leur non-vacuité. À muscler quand la **Story 1.8** (rendu HTML) rendra les champs vides visiblement cassés à l'écran.

À vérifier explicitement à la **Story 1.8** : s'assurer que l'échappement automatique de Jinja2 reste actif sur ce champ, ne jamais utiliser le filtre `|safe` dessus.
